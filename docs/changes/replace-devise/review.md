- [ ] Important: Lockout counter can be bypassed by parallel requests. `register_failed_attempt` reads `failed_attempts` from the loaded record and writes `failed_attempts + 1` with `update_columns`. N concurrent wrong-password requests all read the same value and write the same `+1`, so an attacker who fires bursts gets far more than 20 guesses per lock window. No `rate_limit` exists to cover this (plan decision 16). Devise used an atomic SQL increment (`increment_counter`). Increment in SQL (`UPDATE ... SET failed_attempts = failed_attempts + 1`) and read the result back before the lock decision. — `app/models/concerns/authenticatable.rb:40` →
- [ ] Important: A password reset or a password change does not end other sessions. Devise put the password salt into the session and the remember cookie, so a password change signed out every other browser. Here `reset_password` and `User#update_with_current_password` leave every existing `Session` row valid, and the cookie slides forward one year on each use. A user who resets a password after a compromise keeps the attacker signed in indefinitely. Destroy the account's other sessions when the password changes, and add a test for it (no spec criterion covers this regression yet). — `app/models/concerns/authenticatable.rb:53`, `app/models/user.rb:134` →
- [ ] Important: Sign-in does not rotate the Rails session or the CSRF token. Exposure is low with `force_ssl`, but it is a regression of a Devise control. Read `return_to_after_authenticating` first, then `reset_session` before writing the auth cookie. — `app/controllers/concerns/authentication.rb:38` →
